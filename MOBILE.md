# Mobile

The decision, made 2026-09-08: Bagholder stays local-first on every platform. Nothing leaves the user's device, so there is no server for the apps to lean on, and each app carries the whole model. The native apps are plain native: SwiftUI on iOS, Jetpack Compose on Android, in `ios/` and `android/` of this repository. Each has its own implementation of the model, and the three implementations are kept in agreement by `fixtures/cases`, run through every implementation's tests, so a rule changed in one and not the others fails a PR before it lands.

## What exists

Branch `ios`, PR #63, 2026-09-08:

- **The model, three times.** `model.py` is the reference. `ios/Bagholder/Model.swift` + `ModelView.swift` and `android/model` (Kotlin) are ports of it function for function: normalization, assignment shares, FIFO with option rolls, assumed expiries, FX, round trips, positions, cashflow, KPIs, filters, the equity series and yearly returns against an index, annualized return, drawdown, the dashboard cards, the journal, the Cashflow page. `fixtures/cases` (28 cases from `fixtures/make_fixtures.py`) run through all three (`test_fixtures.py`, `ios/BagholderTests/ModelCasesTests.swift`, `android/model/src/test/.../ModelCasesTest.kt`) and compare the whole view.
- **The iOS app** (`ios/`, SwiftUI, Xcode 26, iPhone 17 simulator): `App.swift`, `Screens.swift` (Dashboard, Trades and the trade detail, Positions and the position detail, Cashflow, the filter sheet, the menu), `Theme.swift` (the page's Nocturne and Light tokens, the spec's formatting), `Charts.swift`, `AppState.swift` (`Book`: the keychain session, the last pull, the journal, the filter set, the pull, the market loop), `Market.swift` (quotes from TMX Money, Cboe Canada, Coinbase and Cboe's delayed option marks; the declared distribution records; the S&P/TSX and TSX 60 closes; daily bars from the TMX and Yahoo chain, weekly and monthly aggregated), `WSPull.swift` (the Wealthsimple pull from the spike, NAV history included).
- **The Android app** (`android/`, Jetpack Compose, compileSdk 34): `MainActivity.kt` (the same screens), `Theme.kt`, `Charts.kt`, `Journal.kt` (`Book`), `Store.kt`, `Market.kt`, `WSPull.kt` (with NAV history and the S&P from FRED), `Queries.kt` (generated from the Swift file). Build: `cd android && ./gradlew :app:assembleDebug` (JDK 17+, `ANDROID_HOME`).
- **Verified** headless: the iOS simulator (`xcrun simctl`, the app container seeded from the fixture cases, `simctl io screenshot`) and the Android emulator (`emulator -avd Medium_Phone_API_35 -no-window`, `adb shell run-as com.bagholder.app` to seed `files/bagholder/`). Every figure on every screen matched the Python model on the same rows, on both platforms, and real bars came through for LUNR. The iOS app has synced a real Wealthsimple session on a phone; Android has not.

Not there yet: intraday timeframes (1H, 4H) on the trade chart, the Midnight theme, Wealthsimple's balance beside a position's quantity (the phone pull does not fetch balances), the equity curve's account switch beyond the account filter.

**Version (2026-09-08):** the apps carry the product version, the same number as `APP_VERSION` in `bagholder.py` (1.5.2 today): iOS as `MARKETING_VERSION` in `ios/Bagholder.xcodeproj/project.pbxproj` (an Info.plist key does not override it), Android in `android/app/build.gradle.kts` (`versionName`). A release bumps all three together; the release's assets are `bagholder-vX.Y.Z-web.zip` (+ `.sha256`) for the desktop updater and `bagholder-vX.Y.Z-android.apk` for Android. Release assets say what they are: `bagholder-vX.Y.Z-web.zip` (+ `.sha256`) for the web app and `bagholder-vX.Y.Z-android.apk` for Android, on the one release page of that version; a phone test build before a merge is attached to the page of the version it carries (e.g. `bagholder-v1.5.2-android.apk` on `v1.5.2`). The desktop updater picks its archive by exact name (`release_assets` in `bagholder.py`) and ignores other assets; the `-web` name needs the updater to know it first (a PR on master), so the archive keeps the old name for the release that ships that change and takes `-web` from the next.

**Side-by-side audit (2026-09-08).** After the user found the Android tab bar had no icons, both apps were captured screen by screen on the same real 6,070 rows (iOS simulator + Android emulator, seeded from the desktop snapshot) and compared: Dashboard (tiles pager, Equity, the Annual returns / P&L / Grade row, By symbol, Review queue), Trades list, trade detail (chart, facts, executions, Journal), Positions list, position detail (facts, lots, Note), Cashflow (tiles, Distributions, Allocation, Positions, History), Filters sheet, menu, empty page, filter chips, sort options. Differences found and fixed on Android in the same day: tab bar icons; header bag mark and filter/menu symbols (were a letter and text glyphs); details now sit over their tab with the tab bar still below and a round chevron back button (were full-screen with a text "Back"); candle-chart fill markers sized in dp (were raw px, a third the size); version 1.0; the filters search focuses on open. Platform-inherent and documented, not "fixed": Wealthsimple's page hides its passkey button inside Android's WebView (WebAuthn is not exposed to an app's WebView without app-domain association) where iOS shows it and then fails — the same gate, presented differently. Rule from here: "the same on both" is only claimed after captures of both apps on the same book have been put side by side, per screen; anything that cannot be the same is tested on the emulator/simulator first and reported before the user finds it.

**Phone conventions (2026-09-08, from the user's testing on a real iPhone; every one applies to both apps):** cards have 12 pt above and below the content and a 24 pt header row; titles are 15 pt semibold; no captions, subtitles or helper lines under a title (no "All accounts", no "Vs S&P 500", no "CAD", no "Outperformed … in N of M years", no "Dividend" beside a history row); tiles come two per page in a swiping row with a 4 pt-dot indicator and a 14 × 4 accent pill for the current page (Dashboard KPIs; Cashflow YTD, Yield on cost, All time, then past years); charts have no value axis on the phone: the figure sits at the card's top right (Equity: the latest point; P&L: the sum in scope; Distributions: the projected month), a long press reads the point under the finger from the first touch, shows its date or month at the bottom under the finger, dims the rest (the equity line and fill keep their colour up to the finger), and holds the page and pager still; bars fill their month's slot 4 pt apart like the page; Annual returns, P&L and Grade vs P&L are one swiping row of equal cards, the years scrolling inside their card; the By symbol header is a sort menu; Cashflow cards are Distributions, Allocation, Positions, History, and a Positions row is symbol + "shares · avg · dist × freq" on the left, "$/mo" over the yield on cost on the right, then Ex-Div and Pay Day. The user tests iOS on their phone and expects Android to carry every change in the same commit.

**Passkey login (2026-09-08): confirmed not achievable in-app; credentials + 2FA is the path.** Proven on the iOS 26.4 simulator and the user's iPhone (26.6.1). The passkey button fetches its WebAuthn options fine, WebKit hands the request to AuthenticationServices, and iOS refuses with ASAuthorizationError 1004 ("no credential provider offered"). Safari on the same phone logs in with the same passkey from the same manager. The difference is not our code (the byte-identical spike build fails today too): iOS runs a passkey ceremony inside a *third-party* app's WKWebView only when the app is (a) listed for `webcredentials` in the relying party's apple-app-site-association — my.wealthsimple.com lists only Wealthsimple's own five app IDs, not ours — or (b) carries `com.apple.developer.web-browser.public-key-credential`, which Xcode rejected for the user's Apple Development account ("not found and could not be included in profile") because Apple grants it only to accounts approved as web browsers. A trading journal will almost certainly be declined if it requests it. ASWebAuthenticationSession / SFSafariViewController would surface the system passkey UI but return only a callback URL, not the site cookies the pull needs, so they do not fit either. The focus/presentation hacks tried for the passkey were removed once it was ruled out: forcing the web view to be first responder on every page load fought the login field and the password manager for focus (the tap-to-select and reach-the-manager lag the user reported), and staging the login behind the menu's dismissal added a second animation before the page appeared. The login now presents directly and does not touch first responder. What remains of the initial-load wait is WebKit's own cold WebContent process launch (~1.7 s), which Safari avoids by keeping a process warm; a background preload could hide it but loads the site before the user asks. Verified again on 2026-09-08 with the app launched from the home screen, no debugger attached: the passkey button still does nothing, so this is not an Xcode artifact. Net: the passkey button cannot work in this app as a non-browser; leave login on email + password + 2FA.

**Login speed (2026-09-08):** the multi-second Connect lag (dead button, then a slow page) was self-inflicted, not the site: a browser loads my.wealthsimple.com instantly on the same phone. Tapping Connect built the WKWebView and started its load synchronously on the main thread, freezing the button, then paid a cold engine and cold cache. Fixed by keeping one warm login web view: `LoginWeb.shared` is a persistent WKWebView, created and told to load the login page ahead of the tap (on app appear when not connected via `book.warmLogin()`, and when the menu opens); the Connect sheet just presents that already-loaded instance, and `reset()` drops the page after a login or a disconnect so the next warm reloads fresh. Two supporting fixes: disconnect clears only session-bearing website data (cookies, local/session storage, IndexedDB, service workers) and keeps the HTTP cache, so a reconnect is not a cold re-download; and the cookie-capture watcher polls once a second and decodes only the two cookies it needs, instead of re-scanning every cookie on every change (that scan storm during the Cloudflare check was the post-load input lag). Verified on the simulator: after warming, tapping Connect shows the fully loaded form at once. Second cause, measured with timestamps and the user's real 6,070 rows seeded on the simulator: the menu's Connect first dismissed the menu sheet and only then presented the login, 579 ms of nothing on the Mac and several times that on the phone in Debug, with no tap feedback. The login now presents from inside the menu sheet, over it (as the spike did): tap to login view is 17 ms. The menu closes itself once the book is connected. The market loop is paused while the login is up, and handleAppear does nothing while it is (the password manager's sheet takes the scene inactive and back). Third and fourth causes, both first-launch only (the user: after Cancel, reopening is instant; the first open after launch is not): (1) a WKWebView outside any window is suspended by WebKit on the device, so the launch-time warm never actually loaded the page, and presenting a web view whose process is suspended makes WebKit wait on the main thread — the warming web view is now parked in the key window behind the opaque root (`LoginWeb.park()`), which keeps its process foreground and the page loading, and is moved into the sheet on present; the sheet also shows its own background first and attaches the web view on the next run-loop turn, so the tap's response never waits on WebKit. (2) The first keyboard of a process costs a few hundred ms and the keyboard's safe-area change made SwiftUI relayout the whole dashboard under the sheet (532 ms main-thread stall on the Mac with the real book, measured with a stall watchdog); the keyboard is now pre-warmed at launch with a hidden text field, and the four tab roots and the login cover ignore the keyboard safe area (pushed detail screens keep theirs), which halved the first-focus stall. What is left on the first focus is the system's own first AutoFill query to the password manager.

**How to judge speed on the phone (2026-09-08, the finding that ended the login-lag chase):** launch from the home screen, not from Xcode's Run. With the debugger attached, WebKit's helper processes and framework loading run under lldb's interception: the phone's own timeline (printed with a temporary probe) showed creating the login web view at 1.46 s and putting it in the window at 1.23 s, 3+ s of main thread, where the Mac takes 100 ms, and the first SwiftUI frame at 1 s; the user then saw a dead app and a dead Connect button. The same build launched from the home screen was snappy everywhere. The login changes made along the way stand on their own merits (the login presents from inside the menu with no dismissal first; one persistent web view, warmed after the first frame and parked in the window behind the root so WebKit does not suspend it; disconnect keeps the HTTP cache; the cookie watcher polls once a second; the market loop pauses behind the login; the tab roots and the login cover ignore the keyboard safe area). The hidden-field keyboard prewarm was removed: on a device it can block launch for seconds.

## The plan

1. **iOS.** Done: the model, the four pages, the details, filters, menu, market data. Next, once the user has tested a real pull: intraday bars, then whatever the test turns up. The old list, for reference: Positions, Cashflow with its tiles and Allocation donut, the trade chart, the filter search. Build and run in the Simulator each round (the Simulator can be driven from Claude Code). One rule: a Swift model change comes with the case that proves it, on both sides.
2. **Android.** Done: the same as iOS. Next: a real pull to confirm the login capture and the sync end to end, then intraday bars alongside iOS. Gradle builds an APK for direct install; the AAB for the Play Store is the same project with one flag.
3. **The Wealthsimple login on a phone** has no Chrome to capture from. Each app does it in its own web view and captures the session cookies from there; the desktop's `_cdp_cookies_from_target` in `bagholder.py` shows which cookies and which fields.
4. **Add cases as rules are touched.** Every model change on any platform comes with a case in `fixtures/cases` if none covers it. The cases are the contract; `SPEC.md` is the meaning.

## Rules that carry over

Everything in `CLAUDE.md` and `SPEC.md`: only what was asked, per-instrument figures in the instrument's currency, aggregates in CAD unlabelled, payout frequency from the fund's record, raw rows never rewritten, nothing synthetic on a chart. A phone screen is a layout of the same figures, not a new definition of them.
